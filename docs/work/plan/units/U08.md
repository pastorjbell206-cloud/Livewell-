## The cause

**1. The static hero loses the LCP race to React's copy of it.**
`prerender-heads.mjs` paints the home hero into the HTML of `/` so the
largest paint is the first paint. Lighthouse named the LCP element as
`main > section.home-hero > ... > p.home-hero__text`. The static shell has no
`<main>`, so the paint being counted was React's, not the HTML's.

What happens: the bundle (68 KB + 60 KB brotli) lands about 78 ms in, around
the first frame. React replaces `#root` before Chrome has recorded when that
frame reached the screen, and Chrome drops a text node removed in that
window as an LCP candidate. React's identical paragraph (same box, same
font, same size) then becomes the only LCP entry, about 80 ms later.
Lighthouse's simulator (Lantern) builds LCP from every request that finished
before the observed LCP plus the CPU work up to it, so the bundle download
and its 4x-throttled evaluation land in LCP. Checked by:

- logging every LCP entry: first paint at 92 to 104 ms, and the one LCP
  entry is React's paragraph at 184 ms;
- blocking the bundle, or delaying it by 60, 150, 300 or 1000 ms: the static
  paragraph is the LCP at first paint, and React's re-render adds no entry.
  Delayed by 20 ms, React's copy wins again. It is a race, which is also why
  CI's number moves from run to run.

This is not only a lab effect. A reader whose bundle is cached (a return
visit) or quick gets the same race, and Speed Insights would record React's
paint.

**2. The portrait, from the legacy CloudFront host, is charged to LCP.**
The portrait `<img>` requests at high priority, and Lantern counts any image
that is not low priority and finishes before the observed LCP. Locally the
image fails at once (the sandbox cannot reach CloudFront), so it never
counted. In CI it loads. To measure it, a local HTTPS stand-in answered for
`d2xsxph8kpxj0f.cloudfront.net` inside Lighthouse's Chrome (host-resolver
rule; nothing left the machine). With only fix 1 in place:

| Stand-in portrait | Performance | LCP |
|---|---|---|
| unreachable (as in the sandbox) | 96, 96, 96 | 2.5 s |
| 184 KB | 88, 87 | 3.6 to 3.8 s |
| 2 MB | 73 | 12.6 s |

73 is exactly the CI pattern. The real file's size is unknown here: it is an
uploaded phone photograph (`IMG_4533_137f3486.jpeg`) drawn at 56 x 70 on a
phone.

Also named by Lighthouse, smaller: `registerSW.js` was a parser-blocking
`<script>` in `<head>` on every page (about 300 ms estimated), and the one
site-wide stylesheet (120 KB, 22 KB brotli) blocks render (about 450 ms
estimated). The CSS is left alone (below).

## What changed

Files: `client/src/lib/static-hero.ts` and `static-hero.test.ts` (new),
`client/src/main.tsx`, `client/src/pages/Home.tsx` (one attribute),
`scripts/prerender-heads.mjs` (one attribute, one comment),

- **`lib/static-hero.ts`, `main.tsx`.** On `/` only, the app mounts once an
  LCP entry inside the static hero has been recorded. It is usually already
  buffered when the bundle runs, otherwise it comes a frame later, and the
  wait is capped at 300 ms. Every other path mounts at once, because
  `vercel.json` serves the home HTML (hero included) as the fallback for any
  path without its own file, and there the hero must not be held on screen.
  A browser without LCP, and a hidden tab (no LCP is reported there), also
  mount at once. On a fast load React now mounts about 50 ms later on `/`,
  behind a hero that is already painted and identical. Six unit tests cover
  each mount-at-once case, the wait, a paint outside the hero (the
  masthead), the timer, and no double mount.
- **Portrait `fetchpriority="low"`** in `Home.tsx` and in the prerendered
  hero, kept mirrored. On a phone the portrait is a thumbnail beside the
  name; it should never compete with the CSS, fonts, and text. A low-priority
  image also stays out of Lantern's LCP whatever its size.
- **`registerSW.js` deferred** (`injectRegister: "script-defer"` in
  vite-plugin-pwa). The script only adds a `load` listener, so behavior is
  the same; it no longer blocks the parser on any page.
- **One portrait constant.** `AuthorBio.tsx` had its own copy of the
  CloudFront URL; it now reads `PORTRAIT_URL` from `positioning.ts`, so Home,
  /about, the author card and the prerendered hero move together.
- **`scripts/bring-portrait-home.mjs`.** From a URL, or a file James
  supplies, it writes one 4:5 crop, cut the way the pages already show it
  (centred, as `object-fit: cover`), to
  `client/public/images/james-bell-portrait.jpg` at 640 x 800 with sharp
  (already a dependency). Only when that succeeds, and only if
  `PORTRAIT_URL` still names CloudFront, it points `PORTRAIT_URL` at
  `/images/james-bell-portrait.jpg`.
- `main.tsx` drops an unused import (`getLoginUrl`) that was already on the
  base commit, so the touched file lints clean.

No reader-facing copy, no new route, no hex, no new surface. One in, one out
does not apply: nothing is added for readers.
